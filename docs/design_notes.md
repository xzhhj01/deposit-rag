# 설계 노트 — 겪은 문제와 해결

RAG 파이프라인 설계문서의 "컬렉션 · 청킹 · 프롬프트를 그렇게 선택한 이유와 겪은 문제, 해결 과정"에 옮길 기록.

---

## 1단계 · 메타 색인 (F2001 ~ F2002)

### 결과
- 금감원 금융상품한눈에 API에서 예금 · 적금 771건 수집 (은행 100 · 저축은행 671), 공시월 2026-10
- `product_meta` 컬렉션에 상품 1개 = 청크 1개, id = `유형:금융사코드:상품코드`
- 두 번 색인해도 771건 유지 (upsert)

### 문제 1 — 상품 전체 텍스트로는 우대조건 검색이 안 된다
| 질문 | 기대 상품 | 상품 전체 텍스트 1청크 | 우대조건 줄 단위 |
|---|---|---|---|
| 대중교통 이용하면 금리 더 주는 상품 | KB맑은하늘적금 | 390위 / 771 | **6위** (1위 NH내가Green초록세상적금도 대중교통 조건 보유 — 정답) |
| 공과금 자동이체하면 우대해주는 적금 | 우리SUPER주거래적금 | 421위 / 771 | **2위** |
| 대중교통 | KB맑은하늘적금 | — | **2위** |

- 원인: 모든 상품 텍스트가 같은 서식(상품명/금리표/만기 후 이자율…)을 공유해 임베딩이 서식에 끌려간다.
  우대조건 한 줄("대중교통 미션")은 긴 텍스트 안의 작은 부분이라 벡터에 거의 반영되지 않는다.
- 시도: 서식을 빼고 요약문만 임베딩 → 오히려 나빠진 경우도 있음 (390위 → 546위). 길이 문제가 아니었다.
- 해결 방향: 우대조건을 **조건 한 줄 = 청크 하나**로 쪼개 따로 색인하고, 상품 점수 = 가장 가까운 조건 줄의 점수.
  조건 탐색(F2011)에서 적용한다. `product_meta`는 상품 1개 = 1청크로 유지한다 (질의응답의 "항상 포함하는 메타 근거"로 쓰고, 검증 4.1의 건수 일치를 지키기 위해).

### 문제 2 — 숫자 조건과 유형은 임베딩이 구분하지 못한다
- "금리 3% 넘는 적금" → 상위 5개 중 4개가 **정기예금**. "적금"이라는 단어도, "3% 넘는"이라는 크기 비교도 보장되지 않는다.
- 해결 방향: 숫자 · 범주 조건은 메타데이터 필터(`kind`, `group`, `best_max_rate`)로 처리하고, 의미 검색은 우대조건처럼 문장으로 된 조건에만 쓴다.
  자연어 조건 → LLM이 필터 값과 의미 조건으로 나눠 추출 → 필터 + 의미 검색 → LLM 최종 선별 (F2011).

## 3단계 · 외부 문서 색인 (F2005)

### 결정 — 문서 범위(scope) 3단계
영화는 "영화마다 관련 문서"가 있지만, 예·적금 771개는 상품마다 위키 문서가 따로 없다. 대부분은 모든 상품이 함께 쓰는 개념 문서다.

| scope | 예 | 청크 id | 검색 범위 필터 |
|---|---|---|---|
| common | 예금보험, 복리, 원천징수 | `common:wiki-ID:순번` | 모든 상품 |
| company | KB국민은행 문서 | `company:국민은행:wiki-ID:순번` | 그 금융사 상품 |
| product | 질문할 때 수집한 문서 (5단계) | `상품ID:wiki-ID:순번` | 그 상품만 |

같은 위키 문서가 공통으로 한 번, 특정 상품의 근거로 한 번 들어가도 scope_key 가 달라 서로 덮어쓰지 않는다.

### 결과
- 공통 18건 · 금융사 29건(은행 16/18, 저축은행 13/79) → 1000자/200자 기준 135청크
- 청크 500자/100자로 바꾸면 268청크, 1000자로 되돌리면 다시 135청크 (검증 4.2)
- 다시 색인할 때 같은 문서의 이전 청크를 먼저 지운다. 지우지 않으면 500자 때 만든 #135~#267 청크가 남아 섞인다.
- 받은 위키 본문은 cache/wiki_pages/ 에 저장 → 두 번째 실행부터 위키 호출 0회 (3분 15초 → 1분 12초, 남은 시간은 임베딩)

### 문제 3 — 위키 검색어 · 넘겨주기가 엉뚱한 문서로 데려간다
- 검색: "단리" → 청풍면(제천시), "중도해지" → 중도우파, "파킹통장" → 맥쿼티
- 정확한 제목으로 받아도: "단리" → 넘겨주기 → "청풍면 (제천시)" (마을 이름 단리)
- 해결: 공통 문서는 제목을 눈으로 확인해 고정하고, 받은 문서 제목이 요청한 제목을 포함하지 않으면 버린다.
  질문할 때의 자동 수집(5단계)에서는 후보 선별 프롬프트(프롬프트 2)가 이 역할을 맡는다.

### 문제 4 — 위키에 한국 예·적금 실무 정보가 얇다
- "이자에 세금이 얼마나 붙어?" → 소득세 · 원천징수 문서가 상위 4개에 없다. 위키에 "이자소득세 15.4%" 같은 실무 수치가 거의 없다.
- "복리" 문서는 134자, "만기"는 93자뿐이다.
- 해결 방향: 종류가 다른 출처(한국은행 경제금융용어 700선 PDF 등)를 함께 색인 → 심화 F2016.

### 문제 5 — "이 은행"처럼 대상을 말하지 않는 질문
- "이 은행은 언제 생겼어?"(카카오뱅크 범위) → 상위 3개가 모두 네오뱅크 공통 문서. 질문에 '카카오뱅크'가 없어서다.
- 해결 방향: 검색할 때 질문 앞에 선택한 상품명 · 금융사를 붙인다 (4단계 retrieve 노드).

## 4단계 · 검색과 생성 (F2006 ~ F2008)

### 구조
`START → retrieve → generate → END` (구조 출력: docs/rag_graph.md)
- retrieve: 선택 상품의 메타 청크(검색 없이 id로, 항상 근거 1번) + 외부 문서 청크(범위 = 공통 + 그 금융사 + 그 상품)
- generate: 프롬프트 3(rag/prompts.py) + 최근 대화 6개

### 문제 6 — 상품명을 붙이면 금융사 질문은 좋아지고 개념 질문은 나빠진다
| 질문 | 질문만 검색 | 금융사 + 상품명 + 질문 |
|---|---|---|
| 이 은행은 언제 생겼어? (카카오뱅크) | 네오뱅크 문서뿐 | 카카오뱅크 문서 1위 (0.43) |
| 단리랑 복리 중에 뭐야? | 복리 문서 1위 (0.65) | 복리 문서가 상위 5개에서 사라짐 |
- 해결: 두 검색어로 모두 찾고 합친다.
- 그런데 거리 값으로 합치면 상품명 검색의 금융사 문서(0.5대)가 늘 이겨 복리 문서가 또 밀려났다.
- 해결: **RRF(Reciprocal Rank Fusion)** — 거리 대신 각 검색에서의 순위로 점수(1/(60+순위))를 더해 합친다.
  두 검색의 상위 결과가 고르게 섞여, 복리 문서가 근거에 들어가고 답에 인용됐다.

### 문제 7 — 메타 청크만으로 충분한 질문에 붙는 무관한 문서
- "이 적금 우대조건 뭐야?" → 외부 문서 5개가 모두 무관 (KB국민은행 0.53, 기준금리 0.59, 예금보험 0.63 …)
- 영향: 토큰 비용 증가, LLM이 무관한 문서를 끌어다 쓸 위험, 화면에 무관한 근거가 보일 위험
- 해결: 거리 0.65 초과는 버리고(DOCS_MAX_DISTANCE), 프롬프트에 "실제로 쓴 근거에만 번호" 규칙,
  화면은 답에 인용된 번호만 표시. 실제로 답은 [근거 1]만 인용했다.

### 문제 8 — 근거 번호를 '언급'만 해도 인용으로 표시된다
- "오늘 서울 날씨?" → "국민은행 상품 정보([근거 1])는 확인되지만 날씨와는 무관합니다" → 화면에 근거 1건으로 표시됨
- 해결: 프롬프트 규칙 4 — 내용을 실제로 썼을 때만 번호를 붙이고, 근거가 없으면 번호를 아예 쓰지 않는다.
  수정 후 "답변에 인용된 근거가 없습니다" 안내가 정상 표시됐다.

### 확인 결과 (검증 4.3)
- Top-k 2 → 외부 문서 2건, Top-k 5 → 5건 (DOCS_TOP_K 환경변수로 비교)
- 답의 금리 숫자가 공시 데이터와 일치 (카카오뱅크 자유적금 6/12/24/36개월)
- 문서에 없는 질문("대중교통 미션 달성 방법")에 추측하지 않고 확인되지 않는다고 답함

## 5단계 · 질문 시점 문서 수집 (F2003 ~ F2004)

### 구조
수집은 그래프 밖, 그래프를 돌리기 전에 한다 — 정의서 F2007 "LangGraph를 검색과 생성 두 개의 노드로".
`collect_for_question()` → `graph(retrieve → generate)`

1. 항목 자체 문서: 상품마다 위키 문서는 없으므로 상품 공시(메타 청크)와 금융사 위키 문서를 항목 문서로 본다.
   금융사 문서는 선별을 거치지 않고 항상 색인한다 (F2004 "어떤 제외 규칙보다 우선").
2. 프롬프트 1(검색어 추출) → JSON 문자열 배열. 공시만으로 답할 수 있는 질문은 [] → 수집 없음.
3. 이미 수집한 검색어 · 같은 질문은 건너뛴다 (cache/collected.json, NF2002).
4. 위키 검색 후보 중 이미 색인된 문서는 후보에서 뺀다.
5. 프롬프트 2(후보 선별) → 제목 · 요약만 보고 고른 번호의 JSON 정수 배열. 고른 문서만 본문을 받는다.
6. scope=product 로 색인. 청크 id = `상품ID:wiki-ID:순번`

### 왜 본문을 받기 전에 고르나 (정의서 2.4)
- 본문 호출 수가 준다. "중도해지" 검색 후보 5개 중 4개가 중도우파 · 중도좌파 · 석가모니 등 — 본문을 다 받았다면 위키 호출 4회와 임베딩이 헛일.
- 동음이의어는 임베딩 거리보다 LLM이 잘 가른다. 거리로는 "단리(마을)"도 금융 질문과 0.6대로 가깝게 나올 수 있다.

### 문제 9 — 주제가 둘 섞인 질문은 이미 색인된 문서도 못 찾는다
- "이자에 세금은 얼마나 떼? 중도해지하면 어떻게 돼?" → 원천징수 · 소득세 문서가 색인돼 있는데도 근거에 없음.
  질문 전체의 임베딩이 두 주제 어디에도 가깝지 않다.
- 해결: 프롬프트 1이 뽑은 검색어도 retrieve 검색어로 함께 쓰고 RRF 로 합친다 → 원천징수(0.44) · 소득세(0.47)가 근거에 들어가 인용됨.

### 문제 10 — LLM은 같은 질문에도 다른 검색어를 낸다
- 같은 질문 두 번: ['소득세','원천징수','중도해지'] → ['원천징수','이자소득','중도해지'] → '이자소득'을 새 검색어로 보고 또 수집.
- 해결: 상품별로 질문 → 검색어를 기록해, 같은 질문이면 검색어 추출부터 건너뛴다. (검증 4.2 "같은 질문을 다시 물었을 때 수집이 다시 일어나지 않는지")

### 문제 11 — 공시만으로 답할 질문에도 수집하고, 억지로 고른다
- "우대금리 조건 뭐야?" → 검색어 ['우대금리','적금'] → 프라임 레이트 · 공공 마이데이터를 골라 색인 (노이즈 + 헛호출)
- 해결: 프롬프트 1에 예시(few-shot) 추가 — 상품 조건 질문은 [] / 프롬프트 2에 "느슨하게 관련된 문서는 고르지 않는다, 빈 배열이 정답일 수 있다"
- 결과: 우대금리 · 최고금리 · 중도해지 · 자동연장 질문 → [] / 예금자보호 · 복리 질문 → 알맞은 검색어

### 남은 한계
- 프롬프트 2는 실행마다 고르는 문서가 조금씩 다르다 (같은 후보에서 [예금보험공사] / [예금보험공사, 뱅크런]).
- 위키에 한국 예·적금 실무 수치(이자소득세 15.4%, 중도해지 이율)가 없어 "확인되지 않습니다"로 답하는 질문이 남는다 → F2016(PDF 등 다른 출처)에서 보완.

## 6단계 · 특화 기능과 조건 탐색 (F2010 · F2011)

### F2010 — 내 조건 기준 실제 금리 판정
- 판단(언어)은 LLM, 계산(숫자)은 코드. LLM: 우대조건 원문을 항목으로 나누고 충족 / 미충족 / 확인 불가 판정.
  코드: 기본금리 + 충족 우대금리, 상한(원문 cap · 공시 최고금리) 적용, 단리 · 복리 이자와 세금 계산.
- 숫자 검사: LLM이 읽어 온 우대금리가 원문에 실제로 있는지 코드로 확인 → 없으면 계산에서 뺀다.
  예) 우리SUPER주거래적금 "금리쿠폰을 적용" — 원문에 숫자가 없어 계산 제외 표시.
- 결과는 범위: 앞쪽 = '충족'만, 뒤쪽 = '확인 불가'까지 다 받는 경우.
- 세율 15.4%는 근거가 아니라 **계산 가정** — config.INTEREST_TAX_RATE, 화면에 "근거"와 "계산 가정"을 나눠 표시.
  (근거 기반 원칙은 LLM이 하는 주장에 대한 것. 계산 상수는 드러내고 바꿀 수 있게 두면 된다.)
- 검산: KB맑은하늘적금 월 50만 원 12개월, 2.65% + 0.1 + 0.4 = 3.15% → 세전 102,375원 × 0.846 = 세후 86,609원 (화면 값과 일치)

### 문제 12 — 판정 기준이 모호하면 LLM이 흔들린다
- "종이통장은 필요 없어요" → '종이통장 줄이기 미션' 미충족으로 판정 (반대)
- "퀴즈는 잘 모르겠어요" → 미충족 (확인 불가여야 함)
- 해결: 판정 기준에 방향 예시 추가 — "같은 방향이면 충족", "안 한다고 분명히 말했으면 미충족", "모르겠다 · 아마는 확인 불가"
- 남은 한계: "잘 모르겠어요"는 두 번 중 한 번 미충족으로 판정 — 모호한 입력은 여전히 흔들린다.

### F2011 — 조건 탐색
LLM이 요청을 필터(유형 · 금융권 · 기간 · 최저금리 · 우대조건 없음)와 핵심어(포함 · 제외)로 나눔 → 코드 필터 →
후보(포함어: 우대조건 줄 단위 의미 검색 / 제외어: 코드로 단어 없는 상품 우선 / 없음: 금리순) → LLM 검증 → 카드 → 대화로 이동

### 문제 13 — 의미 검색어가 길면 핵심이 묻힌다
- 파싱 결과 "대중교통 이용 시 우대금리(추가 금리)를 받을 수 있는 적금"으로 검색 → KB맑은하늘적금이 상위 60줄 밖
- "대중교통"만으로 검색 → 2위. 공통어(우대금리 · 적금 · 금리)가 모든 상품 줄과 비슷해 핵심어를 묻는다.
- 해결: 파싱이 문장 대신 핵심 명사 목록(include_keywords)을 내게 하고, 핵심어마다 검색해 순위를 번갈아 합친다.

### 문제 14 — 부정 조건 "급여이체 없이"
- 의미 검색으로 "급여이체"를 찾으면 급여이체 조건이 '있는' 상품을 가져온다 (반대 방향).
- 해결: 제외어(exclude_keywords)는 의미 검색에 쓰지 않고, 코드로 그 단어가 없는 상품을 앞에 둔다.
- 그래도 검증 LLM이 "급여이체 언급 없음"을 '확인 불가'로 보고 전부 탈락시켰다 (결과 0개).
- 해결: 규칙 "언급이 없다는 것은 '만족'이다" + 후보마다 판정 이유를 먼저 쓰고 마지막에 JSON (먼저 이유를 쓰게 하니 정확해짐).
  설명 문장 속 "[P1]" 괄호 때문에 JSON 파싱이 깨져 → 괄호 위치마다 해석을 시도하는 파서로 교체 (rag/parsing.py).

### 문제 15 — 후보 번호가 하나씩 밀린다
- "청년 적금" 결과에서 상품마다 바로 다음 후보의 이유가 붙음 — LLM이 1부터 매긴 번호를 0부터로 읽었다.
- 해결: 번호를 P1, P2 … 로 바꾸고 상품명도 함께 받아, 번호와 이름이 다르면 이름을 믿는다.

### 문제 16 — 예상 못 한 오류가 나면 화면에 트레이스백이 나온다 (NF2004)
- 서버를 다시 띄우지 않아 예전 모듈이 남아 ImportError → 브라우저에 파이썬 트레이스백 전체가 보였다.
- 해결: .streamlit/config.toml 에 client.showErrorDetails = "none". 상세 오류는 서버 터미널에만 남는다.
  (설정 파일은 실행 위치의 .streamlit/ 에서 읽으므로 project 폴더에서 실행해야 한다.)
